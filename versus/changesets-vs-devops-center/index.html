Change sets vs DevOps Center vs scratch orgs vs unlocked packages

Metadata needs to move from one org to another. What is the vehicle?

Change setsDevOps CenterScratch orgs + CLIUnlocked packages

The matrix

Find your situation in the left column. Green means a committed answer; amber means the honest answer is a trade-off — the note says on what.

Your situationPickWhy
Tiny, one-time change between two long-lived orgs, no git in the pictureChange setsThey work. They also cannot delete, cannot be reviewed as a diff, and cannot be reproduced six months later. Fine for a field on a sandbox you are about to refresh. Not a release process.
Admins who will not live in VS Code, but the team wants git and pull requestsDevOps CenterThe clicky front-end on source-driven development. Work items, environments, promotions. Still git underneath — that is the point. Treat it as the on-ramp, not as a second source of truth beside change sets.
Developers building features in isolation, CI on every commitScratch orgs + CLIDisposable orgs from a project shape. This is how you stop 'works in my sandbox.' Requires a real source repo, a definition file, and the discipline to throw the org away.
A coherent set of metadata that should version, install, and upgrade as a unitUnlocked packagesSecond-generation packaging without the ISV ceremony of a managed package. Unlocked means the subscriber can still see and edit — right for in-house modularization, wrong if you need IP protection.
Need to delete metadata, or deploy a destructive change, as part of the releaseScratch orgs + CLIUnlocked packagesChange sets cannot delete. Destructive changes are a manifest in source-driven land. If your process cannot remove a field, it will accumulate fields forever.
Multiple teams shipping into the same org on different cadencesUnlocked packagesThis is the modularization case. One repo-monolith of all metadata is how teams block each other. Packages (or at least package directories) let you version and install independently — with the dependency graph as the tax.
You have no version control today and a release is due this weekChange setsShip the release. Then start the DevOps Center or CLI conversation before the next one. Do not pretend a change set history is an audit trail.

Rule of thumb

  • Change sets are a trap that looks like a process. Use them only as a stopgap, and write down the date you will stop.
  • Source of truth is git, not an org. Every other choice (DevOps Center, CLI, packages) is a way to keep that honest.
  • Scratch orgs are how developers stop contaminating shared sandboxes. If you cannot recreate an org from the repo, you do not have source-driven development yet.
  • Unlocked packages are for modularizing *your* org, not for pretending you are an ISV. Managed packages (2GP) are the AppExchange / IP-protection answer — different job.
  • If two tools are both 'the process,' you have no process. Pick one vehicle per pipeline.
